## Correctness

- **`.claude/agents/confidence-scorer.md`'s `retrieval_score_avg` fallback
  instruction is unsatisfiable.** It says: "If you weren't handed a
  `hybrid_score` for a doc_id, re-derive it by calling
  `mcp__evidence__get_document`." But `get_document` in
  `evidence-mcp-server/evidence_mcp_server.py` (lines 339-358) returns
  `doc_id, source_id, source_type, title, authors, journal,
  publication_date, confidence_weight, body` — never `hybrid_score` (that
  value only exists as a per-query artifact of `search_corpus`). Worse,
  nothing upstream threads `hybrid_score` this far anyway:
  `evidence-synthesizer`'s claim schema (`.claude/agents/evidence-synthesizer.md`)
  carries only `supporting_evidence: [doc_id]`, dropping the retrieval
  agents' `hybrid_score`. So `confidence-scorer` will almost always hit
  this fallback and be told to do something impossible, silently landing on
  the conservative 0.5 default instead. Effectively, 30% of the documented
  weighted confidence formula (`retrieval_score_avg`) is inert for every
  claim in practice. **Fix:** either have `evidence-synthesizer` pass
  `hybrid_score` through per `doc_id` in its claim output, or rewrite the
  confidence-scorer fallback to just say "treat as unknown, use 0.5" without
  the impossible re-derivation step.

- **Retrieval-agent output schemas are missing `source_id`, which the final
  schema requires.** `.claude/agents/literature-agent.md` and
  `.claude/agents/trial-agent.md` document a per-document output shape
  (`doc_id, title, ..., hybrid_score, key_points`, etc.) that has no
  `source_id` field. But the fixed output schema in
  `.claude/skills/evidence-review/SKILL.md` (mirrored in
  `ui/server.py`'s `RESULT_SCHEMA`) requires every `findings[].sources[]`
  entry to include `source_id`. Neither retrieval agent's contract supplies
  it, and no other pipeline stage's documented output carries it either, so
  the supervisor can only fill this required field by silently re-fetching
  every cited doc via `get_document` at assembly time — a step SKILL.md's
  "Assemble" instruction alludes to only loosely ("fetched or passed through
  from the retrieval agents"). **Fix:** add `source_id` to
  `literature-agent.md`/`trial-agent.md`'s documented output schema so it's
  passed through explicitly, rather than relying on an unstated re-fetch.

## Governance Compliance

- **Undocumented, non-deterministic hooks wired into `.claude/settings.json`
  contradict CLAUDE.md's own hook philosophy.** Beyond the two hooks
  CLAUDE.md documents (`enforce_source_allowlist.py`,
  `audit_evidence_trail.py`), `settings.json` also wires PreToolUse hooks
  for `Bash|Grep` and `Read|Glob` to `graphify hook-guard search` /
  `graphify hook-guard read`. CLAUDE.md is explicit that hooks exist to
  "enforce deterministically what must never depend on the model getting it
  right" — but this hook's effect, observed live throughout this review, is
  to inject directive prose ("MANDATORY... You MUST run graphify before
  reading source files") as `additionalContext`, not an allow/deny decision.
  That's steering-by-suggestion, the exact failure mode CLAUDE.md's
  hooks-vs-model framing warns against, and it is nowhere in CLAUDE.md's
  hook inventory or success-criteria table. Additionally, `graphify --help`
  (the actual installed binary) lists no `hook-guard` subcommand, and
  invoking `graphify hook-guard read` directly with a plausible payload
  produced no output and exit 0 — the mechanism actually producing the
  injected text during this session could not be reproduced/verified by
  directly invoking the wired command. **Fix:** document this hook (or
  remove it) in CLAUDE.md; if kept, it should not phrase its
  `additionalContext` as a directive the model "MUST" obey, and its actual
  runtime behavior should be verified against what's wired in
  `settings.json`.
